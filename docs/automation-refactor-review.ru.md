# Повторный рефакторинг Automation

Проверено 6 октября 2026 года после добавления golden, prompt regression,
adversarial, bias, performance, quality history и qualification evidence.
Основной приоритет — достоверность результата: повреждённые, неполные или
несопоставимые данные должны давать явную ошибку либо неполный результат.

## Исправленные дефекты

| Проблема | Последствие | Исправление |
| --- | --- | --- |
| Четыре независимых парсера JUnit; некоторые сначала превращали properties в словарь | Конфликтующие значения внутри одного testcase незаметно перезаписывались, и отчёт мог пройти | Общий `reporting/junit.py` сохраняет конфликты внутри элемента и между фазами, исходные ошибки и отдельные failure/error outcomes |
| Контрольная сумма prompt-отчёта вычислялась повторным чтением XML | Хеш мог относиться к другой версии файла | JUnit разбирается и хешируется из одного массива байтов |
| Stability сравнивал служебные capture ID как настройки эксперимента | Независимые запуски одинаковой конфигурации считались несопоставимыми | Общая нормализация удаляет только конечный capture-маркер и сохраняет исходные настройки |
| Группировка stability теряла имя модуля | Разные одноимённые тесты могли выглядеть как нестабильные повторы одного сценария | Имя класса/модуля входит в ключ группы и сохраняется в результате |
| Performance доверял сохранённым бюджетам и неполной metadata | Неправильные budgets, bool вместо чисел или RAG без provenance могли пройти сравнение | Повторная строгая валидация попыток, бюджетов, времени и сводок; обязательные условия сравнения |
| Для health сохранялся LLM timeout | Отчёт неверно описывал фактические условия запроса | Записывается HTTP timeout; для RAG сохраняется LLM timeout |
| Capture/performance несовместимость обнаруживалась в теле теста | Workspace и индекс готовились до заведомой ошибки запуска | Проверка перенесена в collection после отбора тестов, до внешних фикстур |
| Qualification verifier проверял только перечисленные файлы | Изменение manifest status или пересчитанный поддельный trace могли считаться корректными | Результат пересчитывается из упакованных JUnit, плана, данных и исходников; сверяются outcomes, scope, checksums и manifest |
| В framework checksum отсутствовали вложенные `conftest.py` | Изменения подготовки UI/unit-тестов не меняли baseline | В checksum и пакет включены все `tests/**/conftest.py` |
| Пути плана допускали неоднозначные формы | Один файл мог иметь несколько разных имён в evidence | Только канонические относительные пути; checksum и разбор теста используют одни и те же прочитанные байты |
| Три каталога падали с AttributeError/TypeError/re.error | Вместо понятной ошибки конфигурации получался внутренний сбой collection | Общая валидация JSON-объектов, строк и regex; проверка типов lookup-полей и дублирующихся JSON-ключей |
| Live faithfulness не пересчитывал оценку по verdicts | Некорректное значение метрики могло попасть в completed report | Общая проверка live/saved result; при наличии raw judge calls сохранённая сводка должна совпадать с ними |
| Precision и recall читали и проверяли один файл отдельно | В сводку могли попасть две версии evidence | Один снимок байтов и один валидированный результат для обеих метрик; dataset используется повторно внутри сборки |
| История доверяла cached prompt/judge hashes и повторно читала входы | Подмена конфигурации или замена файла во время сборки могла остаться незамеченной | Хеши сверяются с содержимым; quality report сохраняет хеши прочитанных evidence, snapshot проверяет их повторно |
| `run_id` мог содержать путь; повторное seal меняло checksum | Запись за пределы history или некорректный checksum после повторного seal | Безопасный идентификатор файла; идемпотентный seal |
| JSON сразу записывался в конечный файл | Ошибка сериализации или конкурентное чтение оставляли неполное evidence | Сериализация с запретом NaN/Infinity, закрытый временный файл с mode 0600, атомарная публикация без перезаписи и очистка временного файла |

## Организация кода

- `datasets/validation.py` задаёт общие правила для проверенных каталогов.
- `core/provenance.py` нормализует конфигурацию без изменения входного объекта.
- `reporting/junit.py` отвечает за чтение и объединение фаз JUnit.
- `performance/runner.py` задаёт единые бюджеты и валидирует сохранённые попытки.
- `performance/reporting.py` сохраняет измерения и ошибки до применения acceptance gate.
- Qualification восстанавливает исходную область требований из копий определений.

Тестовые сценарии продолжают использовать прежние пути, фикстуры и CLI-флаги.
Новые зависимости, повторы генерации и изменения acceptance thresholds не добавлены.
Golden/catalog/policy-файлы сохранены без изменения ожиданий и хешей.

## Совместимость сохранённых результатов

В performance metadata теперь обязательны `machine` и фактический `timeout`.
Для RAG также обязательны policy/dataset hashes, case, generation model,
model digest и configuration. Неполные старые отчёты дают `incomparable`;
добавлять отсутствующие сведения задним числом не следует. Нужен новый baseline.
`machine` — имя хоста; оно не описывает GPU, фоновые процессы или холодную загрузку.

В stability добавлено поле `classname`. Конфликты JUnit больше не скрываются
порядком properties. Итоговый статус при противоречивой metadata — неполный.

История требует prompt/configuration, все три judge configuration и хеши
исходных оценок. Ранее корректно сформированные snapshots уже содержат эти поля.
Неполные или изменённые snapshots отклоняются, а прежние файлы не переписываются.
Историю следует пополнять последовательно: дедупликация одинакового sample при
нескольких независимых producer-процессах пока не является поддерживаемым режимом.

Файлы evidence публикуются через hard link в той же директории. Это проверено
на локальной файловой системе; хранилище должно поддерживать hard links.

Новый framework checksum учитывает вложенные фикстуры. Чтобы получить evidence
для текущего кода, тесты необходимо выполнить заново. Проверка копий пакета
не требует доступа к первоначальному checkout и продолжает работать после переноса.

Регрессии сначала воспроизвели ошибки на исходном коде. Unit-тесты запрещают
неподменённые HTTP-вызовы. Отдельные проверки проверяют порядок properties,
повреждение и замену evidence, перенос пакета, конкурентную публикацию JSON,
невалидные бюджеты и отказ CLI до подготовки внешних ресурсов.

Результаты находятся в игнорируемой Git директории `automation/reports/refactor-r2/`.
Итоговые unit/coverage, integration, saved-quality, history и IQ/OQ-пакет — в `final/`;
Chromium JUnit — `browser.xml`. Локальные результаты не означают, что GitHub Actions
уже выполнялся для этих изменений.

## Оставшиеся границы

Regex-проверки фактов остаются ограниченными acceptance checks: присутствие фразы
не доказывает отсутствие отрицания или противоречия. Метрики judge и текущие
пороги остаются экспериментальными и требуют отдельной калибровки.

DOM-локаторы и capture parser привязаны к AnythingLLM 1.16.2. Полный application UI
и PQ matrix в этом повторном рефакторинге не запускались. Новые ответы модели и
judge-оценки не генерировались; OQ проверяет реальное embedding/indexing.

Проверка qualification выявляет расхождение результата с сохранёнными входами.
Unsigned manifest и JUnit не удостоверяют автора и не защищают от полной
согласованной замены всех файлов. Успешный IQ/OQ-пакет сохраняет статус pending
human review и не заявляет полноту PQ или GxP compliance.
